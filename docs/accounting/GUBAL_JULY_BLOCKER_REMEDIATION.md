## 7 · البنك بالدولار — الوجود غير مُثبَت

فحصتُ سجلّ الدفع في الكود والإنتاج:

```
حقول Payment    invoice_id · payment_type · payment_method · currency
                amount · payment_date · reference · notes
```

**لا حقل حساب بنكي إطلاقاً.** ودفعة Navtor: `payment_method = bank_transfer` ·
`reference = null` · `notes = null`.

```
هل لدى Sivamar حساب دولاري؟          لا يمكن إثباته من النظام
أي حساب استُخدم فعلاً؟                غير مسجَّل
```

**لم أقترح إنشاء بنك دولاري** — الشرط الذي وضعتَه لم يتحقّق.

⚠️ **وهذا يمنع دورة Navtor كلها**، لأن الاحتمالين كليهما مسدود:

```
أ · حساب دولاري فعلي     → غير مُثبَت
ب · سداد من حساب اليورو  → يلزم المبلغ اليوروي الذي خصمه البنك — غير مسجَّل
```

⚠️ **و`1010 Bank — EUR` بلا `currency_restriction`** فسيقبل سطراً دولارياً بصمت.
الاسم يقول EUR والقيد لا يمنع غيره. **يُقترح ضبط `currency_restriction = 'EUR'`
على `1010`** — تعديل صف قائم لا حساب جديد.

## 8 · سياسة تاريخ السعر

يُوثَّق لكل سعر: تاريخ المعاملة المطلوب · تاريخ نشر ECB المستخدم فعلاً · مرجع

## 9 · قاعدة قلب سعر ECB

```
ECB ينشر        1 EUR = X USD
النظام يخزّن      currency_from=USD · currency_to=EUR · rate = 1 USD = Y EUR
القاعدة          Y = 1 / X
```

```
التخزين      numeric(18,8)  ← دقة المخطّط الحالية
الحساب       عشري لا ثنائي عائم
```

⚠️ **مسار الحساب الحالي عائم ثنائي:** `createFxRate` يمرّ بـ`Number(body.rate)`،
والمحرّك يستخدم `num(fx.rate)`. فالقلب يجب أن يتمّ **خارج النظام بحساب عشري**
ويُدخل جاهزاً بثماني خانات — لا يُحسب `1/X` داخل الطلب.

⚠️ **إدخال سعر ECB بلا قلب يضخّم كل مبلغ دولاري نحو 15 ضعفاً.** أخطر خطأ
محتمل في التجربة، ولا حارس آليّاً يمنعه اليوم.

## 10 · فجوة اعتماد أسعار الصرف

```
السياسة    كل سعر يُرحَّل به يجب أن يكون معتمَداً
الواقع     if (fx.source === 'MANUAL_APPROVED' && !fx.approved_by) throw
           ⇒ سعر ECB يُرحَّل به بلا اعتماد
```

### أصغر تعديل يحقّق السياسة

**تغيير سطر واحد** في `accounting-posting.ts`:

```ts
if (!fx.approved_by) {
  throw new UnprocessableEntityException(`${at}: سعر صرف غير معتمَد — لا يصلح للترحيل`);
}
```

يستبدل الشرط المقصور على `MANUAL_APPROVED`. **بلا تغيير مخطّط.**

### مسار اعتماد جديد

```
POST /api/accounting/fx-rates/:id/approve
@RequireScreen(SCREEN_ACCOUNTING_POSTING)
يضبط approved_by = المستخدم المنفِّذ · approved_at = الآن
```

**فصل الواجبات بالشاشات القائمة، بلا دور جديد وبلا اسم شخص مخترَع:**

```
الإنشاء     SCREEN_ACCOUNTING_SETUP     ← موجود ويحرس POST /fx-rates
الاعتماد    SCREEN_ACCOUNTING_POSTING   ← موجود ويحرس ترحيل القيود
```

`created_by` و `approved_by` و `approved_at` و `source` و `source_reference`
كلها محفوظة أصلاً.

**ولا اعتماد تلقائي لأن المصدر ECB** — `createFxRate` يضع `approved_by = null`
لكل مصدر عدا `MANUAL_APPROVED`.

⚠️ **تناقض متبقٍّ:** قيد `chk_fx_manual_approved` = `source <> 'MANUAL_APPROVED'
OR approved_by IS NOT NULL` **يفرض** اعتماد السعر اليدوي لحظة إنشائه، فلا يمكن
إنشاؤه مسوّدة. إزالة هذا الاعتماد الذاتي تتطلّب **إسقاط القيد** — تغيير مخطّط.
**التجربة تستخدم ECB وحده فلا تحتاجه.** يُسجَّل ديناً.

## 11 · فجوة عدم تعديل أسعار الصرف

فُحصت الهجرة: حماية عدم التعديل موجودة على `journal_entries` و `journal_lines`
**فقط**. **لا حماية على `accounting_fx_rates`.**

فسعر استُخدم في قيد مُرحَّل **قابل للتعديل اليوم** — ولا يغيّر ذلك أرقام القيد
المُرحَّل (فـ`journal_lines` تخزّن `fx_rate` و `debit_eur` منسوخين)، لكنه **يهدم
أثر التدقيق**: يصير القيد مستنداً إلى سعر لم يعد موجوداً بقيمته.

### التصميم المقترح — لا يُنفَّذ

```sql
CREATE FUNCTION accounting_fx_immutable() RETURNS TRIGGER AS $$
BEGIN
  IF EXISTS (SELECT 1 FROM journal_lines jl
               JOIN journal_entries je ON je.id = jl.entry_id
              WHERE jl.fx_rate_id = OLD.id
                AND je.status IN ('posted','reversed'))
  THEN
    IF TG_OP = 'DELETE' THEN
      RAISE EXCEPTION 'سعر صرف مستخدَم في قيد مُرحَّل لا يُحذف';
    END IF;
    IF NEW.rate <> OLD.rate OR NEW.rate_date <> OLD.rate_date
       OR NEW.source <> OLD.source
       OR NEW.currency_from <> OLD.currency_from
       OR NEW.currency_to <> OLD.currency_to
    THEN
      RAISE EXCEPTION 'سعر صرف مستخدَم في قيد مُرحَّل لا يقبل تعديل القيمة أو التاريخ أو المصدر';
    END IF;
  END IF;
  RETURN COALESCE(NEW, OLD);
END; $$ LANGUAGE plpgsql;

CREATE TRIGGER trg_fx_immutable BEFORE UPDATE OR DELETE ON accounting_fx_rates
  FOR EACH ROW EXECUTE FUNCTION accounting_fx_immutable();
```

يسمح بتعديل `approved_by`/`approved_at` (فالاعتماد واقعة لاحقة مشروعة) ويمنع
تغيير جوهر السعر.

⚠️ **تحذير `synchronize`:** المشغِّل خارج بيانات TypeORM. الإنتاج `synchronize:
false` فلا خطر هناك، لكن أي بيئة تطوير تشغّله قد تُسقطه.

مالي**. الفجوة موثَّقة وتحتاج قراراً مستقلاً.
