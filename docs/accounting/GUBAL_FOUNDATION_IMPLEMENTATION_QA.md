## 5 · إنفاذ اعتماد أسعار الصرف

```ts
// قبل
if (fx.source === 'MANUAL_APPROVED' && !fx.approved_by) throw
// بعد
if (!fx.approved_by || !fx.approved_at) throw
```

**الاعتماد شرط ترحيل لكل مصدر.** `ECB` لم يعد استثناءً، ومعتمِدٌ بلا ختم زمني
اعتمادٌ ناقص لا اعتماد.

و`createFxRate` لم يعد يعتمد شيئاً ذاتياً:

```ts
approved_by: null,  approved_at: null   // لكل مصدر بلا استثناء
```

## 6 · إنفاذ منع الاعتماد الذاتي

مفروض في **ثلاث طبقات**، لا في الشاشة وحدها:

```
1 · الخدمة    approveFxRate  →  ForbiddenException إن كان المعتمِد هو المُنشئ
2 · المحرّك     prepareLines   →  يرفض الترحيل بسعر أنشأه معتمِدُه
3 · قاعدة البيانات   chk_fx_no_self_approval
                    approved_by IS NULL OR created_by IS NULL OR approved_by <> created_by
```

الطبقة الثالثة تحرس حتى ما يتسلّل من خارج التطبيق.

### حارس اتجاه ECB

كل استجابة سعر تحمل اتجاهها منطوقاً بدل أن يُستنتج من أسماء الأعمدة:

```json
{ "rate_label": "1 USD = 0.87 EUR",
  "inverse_label": "1 EUR = 1.14942529 USD",
  "is_approved": false }
```

القاعدة الموثَّقة `Y = 1 / X` تُحسب **عشرياً خارج مسار الطلب** وتُدخل جاهزة
بثماني خانات. **ولم يُبنَ مزوّد ECB تلقائي** — توسّع غير لازم الآن.

## 8 · عدم تعديل أسعار الصرف

مشغّل على مستوى قاعدة البيانات. السعر المستخدَم في قيد `posted` أو `reversed`:

```
rate · rate_date · source · currency_from · currency_to · legal_entity_id   لا تُعدَّل
DELETE                                                                      مرفوض
source_reference · الاعتماد                                                 تبقى قابلة للتحديث
```

**قاعدة التدقيق محفوظة:** `journal_lines` تخزّن `fx_rate` و `debit_eur` و
`credit_eur` **منسوخة**، فالقيد التاريخي مكتفٍ بذاته — ولا تُعيد التقارير حسابه
من القيمة الحالية في `accounting_fx_rates`. مُثبَت بالفحص `I8`.

## 9 · معمار الاستلام

**جدول مستقل لا أعمدة على `invoices`:**

```sql
goods_service_receipts (
  id · invoice_id · receipt_type · received_date · received_by · received_by_name
  reference · notes · attachment_id · is_partial · created_at · created_by )
```

```
الأنواع     GOODS_RECEIVED · SERVICE_CONFIRMED · MANAGEMENT_RECEIPT_CONFIRMATION
```

حقلٌ منطقي على الفاتورة كان سيفرض هجرة ثانية عند أول تسليم جزئي. الجدول يقبل
**وقائع متعدّدة بتواريخ مختلفة وأنواع مختلفة** لفاتورة واحدة — مُثبَت (`R12`:
أربع وقائع لفاتورة واحدة).

**الواقعة دليل فلا تُعدَّل ولا تُحذف** — التصحيح بتسجيل واقعة جديدة. الملاحظات
وحدها قابلة للتحديث. و`ON DELETE RESTRICT` يمنع حذف فاتورة لها وقائع.

RLS مفعَّل و`REVOKE` على `anon`/`authenticated` كما جرى على الثمانية والعشرين.

### إثبات على PostgreSQL 18.4 حقيقي

```
PASS 40 · FAIL 0
```

`docs/migrations/gubal-foundation-pg-proof.js` — ينفّذ ملفَّي SQL أنفسهما، لا
يعيد بناءهما، ولا يضيف اعتمادية للمشروع.

⚠️ **عيبان حقيقيان كشفهما الإثبات وأُصلحا:**

**1 · فخّ تراجع.** القواعد الجديدة تسمح بسعر يدوي **مسوّدة**، والقيد القديم
`chk_fx_manual_approved` يمنعه. فوجود صفّ واحد كهذا كان **يجعل التراجع
مستحيلاً** برسالة غامضة من Postgres. الحلّ: `DOWN` يفحص أولاً ويتوقّف برسالة
تقول ما المانع وما العمل — لا `NOT VALID` يُبقي مخالفات بصمت، ولا حذف تلقائي
يمحو بيانات مالية أثناء تراجع.

**2 · `COALESCE(NEW, OLD)`** على نوع سجلّ في `DELETE` — نفس فخّ P1.1A. استُبدل
بفرعَي `TG_OP` صريحين.

⚠️ **تحذير `synchronize`:** المشغّلات والقيود خارج بيانات TypeORM. الإنتاج
`synchronize: false` فلا خطر، لكن أي بيئة تشغّله قد تُسقطها.

# ملحق · حادثة إنتاج عند النشر

**الخدمة سقطت. المدّة ≈ 6 دقائق. صفر أثر مالي.**

## ما حدث

النشر انهار عند الإقلاع فور دفع كود الأساس. الإنتاج ردّ `502` و`000`.

```
Nest can't resolve dependencies of the ScreenGuard (Reflector, ?).
Please make sure that the argument ScreenAuthzService at index [1]
is available in the ReceiptsModule module.
```

## السبب الجذري

`CommonAuthzModule` **ليست `@Global()`**. كل وحدة تستعمل `ScreenGuard` تستوردها
صراحةً — والتسع عشرة وحدة القائمة كلها تفعل. و`ReceiptsModule` التي كتبتُها
استوردت `TypeOrmModule` وحدها.

**سطر واحد ناقص.**

## لماذا لم تمسكه البوّابات

```
tsc            لا يفحص حقن التبعيات
npm run build  لا يُركّب رسم الوحدات
384 اختباراً    كلها دوالّ خالصة — لا واحد منها يُقلع التطبيق
```

**أضفتُ وحدة Nest جديدة ولم أُقلع التطبيق ولو مرّة.** الخلل في المنهج لا في
الشيفرة: البوّابات التي اعتمدتُها لا تستطيع رؤية هذا الصنف من الأخطاء أصلاً.

## المعالجة

```
1  git revert للكود  →  الخدمة عادت خلال ~20 ثانية من إعادة النشر
2  تشخيص السبب من رسم التبعيات لا من التخمين
3  اختبار تركيب وحدة يُركّب الرسم فعلاً — كُتب قبل الإصلاح
4  إثبات أنه يفشل بإزالة السطر ويمرّ بإعادته
5  تدقيق التسع عشرة وحدة الأخرى — كلها سليمة، الحالة وحيدة
```

`src/modules/receipts/receipts.module.spec.ts` يُحاكي عمومية
`TypeOrmModule.forRoot` بوحدة عامّة مكافئة، وتبقى واردات الوحدة نفسها محلّ
الاختبار.
