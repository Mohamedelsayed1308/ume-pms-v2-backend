# مرتّبات أطقم السفن — دليل التشغيل

الشاشة: `/dashboard/fleet-crew-salaries`
الواجهة البرمجيّة: `api/crew-salaries`
الوحدة: `src/modules/crew-salaries`

## خطّة النشر

**تجهيزٌ لا إذن.** كلّ خطوةٍ هنا تُنفَّذ بطلبٍ صريح من المالك، بالترتيب، وتُسجَّل نتيجتها قبل التالية.
لا تُنفَّذ الهجرة ولا يُتّصل بقاعدة الإنتاج إلّا في خطواتها.

### ما تحقّق محلّيّاً وما ينتظر البيئة الفعليّة

| البند | محلّيّاً (PostgreSQL مؤقّتة تحاكي أدوار Supabase) | على البيئة الفعليّة |
|---|---|---|
| الهجرة صعوداً وتكراراً ونزولاً ببوّابتها | مُختبَر (`migration.pg-spec`) | ينتظر |
| RLS على الأحد عشر، وسحب صلاحيّات anon وauthenticated وservice_role وPUBLIC | مُختبَر، وملفّ الفحص يكشف أيّ خللٍ فيها | ينتظر (ملفّ الفحص + طلب Data API) |
| دور الباك مالكٌ للجداول ويعمل رغم RLS | مُختبَر | ينتظر (ملفّ الفحص، البند ٥) |
| القيد الفريد على `exchange_rates.month` | مُختبَر في ملفّ الفحص قبل الهجرة | ينتظر |
| الإقلاع بوضع الإنتاج بلا `synchronize` على جداول الهجرة | جُرّب في المتصفّح (الجولة الثالثة) | ينتظر |
| تسجيل الدخول، وحارس الشاشة، والاعتماد للمعتمد وحده | مُختبَر، وجُرّب بحسابين اختباريّين | ينتظر (حساب المالك الفعليّ) |

### الخطوة ١ — نسخةٌ احتياطيّة قبل أيّ تغيير في القاعدة

- نسخة Supabase اليوميّة: تُفتح لوحة المشروع ← Database ← Backups، ويُسجَّل تاريخ آخر نسخةٍ ناجحة.
- ونسخةٌ مستقلّة على جهاز المالك (`pg_dump`) بسكربته المحلّيّ (على الجهاز، خارج الريبو عمداً — فيه مساراتٌ محلّيّة):

```
powershell -ExecutionPolicy Bypass -File scripts\backup-db.ps1
```

**المتوقَّع:** ملفّ نسخةٍ بحجمٍ غير صفريّ، وقراءة فهرسه تنجح:

```
pg_restore --list <ملف النسخة> | Select-Object -First 5
```

### الخطوة ٢ — نشر الواجهة أوّلاً

دمج طلب الفرونت إلى `main` (Vercel ينشر تلقائيّاً).

**المتوقَّع:**
- نشر Vercel للإنتاج «Ready».
- بطاقة الأسعار في مركز التقارير: الحفظ ينجح مع الباك القائم (يقرأ `rates` ويتجاهل `base`).
- شاشة المرتّبات تظهر في القائمة للأدمن وحده، وتعرض «تعذّر تحميل البيانات» حتّى يُنشر الباك (المسار غير موجود بعد). لا تُمنح لأحد.

### الخطوة ٣ — إعادة تحميل الصفحات المفتوحة

نشر الواجهة لا يغيّر JavaScript في صفحةٍ مفتوحة. يُعاد تحميل كلّ تبويبٍ مفتوح على النظام (بطاقة الأسعار خصوصاً).

**المتوقَّع:** صفحةٌ لم يُعَد تحميلها يُرفض حفظ أسعارها بعد نشر الباك برسالة 428 «حدِّث الصفحة» — لا استبدال أعمى للشهر.

### الخطوة ٤ — فحص ما قبل الهجرة (للقراءة فقط)

```
node scripts/run-migration.js docs/crew-salaries-verify.sql
```

**المتوقَّع:**

```
NOTICE: OK 1: exchange_rates.month فريد
NOTICE: OK 2: الهجرة لم تُطبَّق بعد — لا جدول مرتّبات (فحص ما قبل الهجرة انتهى)
```

وإن ظهر `CHECK FAILED: لا قيد فريد` يتوقّف النشر هنا — لا هجرة قبل إصلاحه بقرار.

### الخطوة ٥ — الهجرة

```
node scripts/run-migration.js docs/crew-salaries-up.sql
```

**المتوقَّع:**

```
NOTICE: قبل الهجرة: crew_salary_cycles غير موجود — يُنشأ
NOTICE: بعد الهجرة: الجداول الأحد عشر موجودة، وRLS مفعّلة، والوصول المباشر مسحوب
```

الملفّ معاملةٌ واحدة: أيّ فشلٍ يتراجع عنها كلّها ولا يترك جداول ناقصة. وإعادة تشغيله آمنة (`IF NOT EXISTS`).

### الخطوة ٦ — فحص ما بعد الهجرة (للقراءة فقط)

الأمر نفسه في الخطوة ٤. **المتوقَّع:** `OK 1` حتّى `OK 7`، ثمّ أعداد الصفوف (أصفار)، ثمّ:

```
NOTICE: OK: كلّ الفحوص نجحت
```

والبند ٥ يطبع دور الاتّصال (دور الباك) ويتحقّق أنّه مالك الجداول.

### الخطوة ٧ — نشر الباك ومتغيّر المعتمد

أوّلاً المتغيّر على Railway (قبل النشر أو معه):

```
CREW_SALARY_APPROVER_USER_ID=8712bd6f-1880-4fd7-9a7d-8e9976e88eb1
```

أكّد المالك في ٢٧ سبتمبر ٢٠٢٦ أنّ هذا حسابه (`mohamed@ume.com`) وأنّه المعتمد الوحيد. غيابه أو فساده = كلّ اعتمادٍ مرفوض.

ثمّ دمج طلب الباك إلى `main` (Railway ينشر تلقائيّاً).

**المتوقَّع:**

```
GET https://ume-pms-v2-backend-production.up.railway.app/api/health            → 200
GET https://ume-pms-v2-backend-production.up.railway.app/api/crew-salaries/permissions → 401 بلا دخول
```

وسجلّ الإقلاع بلا خطأ حقن تبعيّات، وبطاقة الأسعار (بعد إعادة التحميل) تحفظ.

### الخطوة ٨ — أمان الجداول على Supabase نفسه

1. ملفّ الفحص مرّةً ثالثة بعد نشر الباك — **المتوقَّع** «OK: كلّ الفحوص نجحت».
2. طلبٌ من Data API بمفتاح `anon` (مفتاحٌ عامّ بطبيعته) — يُنفّذه المالك:

```
curl.exe -s "https://<project>.supabase.co/rest/v1/crew_salary_cycles?select=id&limit=1" -H "apikey: <anon key>" -H "Authorization: Bearer <anon key>"
```

**المتوقَّع:** رفض — رمز `42501` («permission denied for table crew_salary_cycles»)، لا مصفوفة بيانات.
ويُكرَّر لـ `crew_salary_bank_accounts` و`crew_salary_export_rows`.

### الخطوة ٩ — الدخول وصلاحيّات الشاشة والاعتماد

يجرّبها المالك بحسابه، ثمّ بحسابٍ آخر (لا يُكتب هنا أيّ كلمة مرور):

| الحساب | المتوقَّع |
|---|---|
| المالك (`mohamed@ume.com`) | الشاشة تفتح · تبويب «المراجعة والاعتماد»: «أنت صاحب صلاحية الاعتماد» · تبويب «الحسابات»: زرّ الاعتماد متاح |
| أدمن آخر | الشاشة تفتح (الأدمن يتجاوز قوائم الشاشات — انظر «يحتاج قرار المالك» أدناه) · الاعتماد معطَّل: «الاعتماد لصاحب الصلاحية المعيَّن وحده» · ومحاولته المباشرة ترجع 403 |
| مستخدمٌ غير أدمن بلا الشاشة في قائمته | الشاشة لا تظهر، ومساراتها ترجع 403 |

### الخطوة ١٠ — منح الشاشة بعد اجتياز التحقّق

من شاشة المستخدمين: إضافة `/dashboard/fleet-crew-salaries` لمن يلزم من غير الأدمن. وتعديل أسعار الشركة يبقى لمن يملك شاشة التقارير.

### الخطوة ١١ — سلامة البيانات

استيراد رسالة الشهر وتصديري CFM، ومطابقة الإجماليّات بأرقام المالك المعروفة. عيّنة أغسطس لا تُعتمد نهائيّاً قبل سعر أغسطس وقيمة لاشينج 379 (انظر «البيانات المعلَّقة»).

### يحتاج قرار المالك قبل الخطوة ٧

**الأدمن يرى الشاشة فور نشر الباك.** حارس الشاشات في المنظومة كلّها يمرّر كلّ أدمن دون قائمة (`ScreenAuthzService.can`)، فكلّ أدمن يستطيع — قبل «منح الشاشة» — العرض والاستيراد والتقديم وتسجيل الحسابات (لا الاعتماد). الخياران:
- **قبول ذلك** بعد التحقّق من قائمة الأدمن الحاليّة على الإنتاج.
- **أو إضافة مفتاح تفعيلٍ للميزة** (متغيّر بيئة يُغلق مسارات المرتّبات إلّا للمعتمد حتّى يُفتح) — تغييرٌ صغير في الباك يلزمه اختبارٌ وإعادة مراجعة، ولا يمسّ قاعدة الأدمن العامّة.

## خطّة التراجع

**لا يُحذف جدول مرتّباتٍ ولا تُفقد بياناته في أيّ تراجعٍ تلقائيّ.**

| ما يُتراجع عنه | كيف | ملاحظة |
|---|---|---|
| الباك | Railway ← Deployments ← إعادة نشر النسخة السابقة، أو `git revert` لـ commit الدمج على `main` ثمّ دفعه | `synchronize` معطَّلٌ في الإنتاج: الكود القديم لا يمسّ الجداول الجديدة، فتبقى ببياناتها بلا استعمال. والباك القديم يقبل بطاقة الأسعار الجديدة (يتجاهل `base`). |
| الواجهة | Vercel ← Deployments ← «Promote to Production» للنسخة السابقة، أو `git revert` لـ commit الدمج | يُتراجع عنها **بعد** الباك أو معه: بطاقة الأسعار القديمة لا ترسل `base`، فيرفض الباك الجديد حفظها (428) ما دام قائماً. |
| متغيّر المعتمد | يُترك | بلا الباك الجديد لا أثر له. |
| الهجرة — لا بيانات بعد | `docs/crew-salaries-down.sql` مسموح | بوّابته تتحقّق أنّ الجداول الأحد عشر فارغة، وإلّا ترفض. |
| الهجرة — دخلت بيانات فعليّة | **تُترك الجداول كما هي** | محميّةٌ بـ RLS وسحب الصلاحيّات، ولا يقرؤها إلّا الباك الجديد. حذفها بقرارٍ مكتوب من المالك وحده، بعد نسخةٍ احتياطيّة وتصدير البيانات (كشوف المراجعة والدفعات)، ثمّ `crew_salary.force_drop=yes`. |

أمر النزول المُجبَر للتوثيق فقط — لا يُنفَّذ إلّا بقرارٍ مكتوب بعد النسخة والتصدير:

```
PGOPTIONS='-c crew_salary.force_drop=yes' node scripts/run-migration.js docs/crew-salaries-down.sql
```

قبل الإنتاج، على مشروع Supabase منفصل (أو فرعٍ منه) وباكٍ وفرونتٍ موجَّهٍ إليه:

```
NEXT_PUBLIC_API_URL=<عنوان باك البيئة المنفصلة>
```

وحسابان اختباريّان: موظّفٌ بالشاشة، ومالكٌ هو المعتمد (`CREW_SALARY_APPROVER_USER_ID` = معرّفه في تلك البيئة). سعر اختبارٍ معلَن (لا سعر أغسطس الفعليّ).

## البيانات المعلَّقة

- **سعر EUR/USD لأغسطس ٢٠٢٦** و**قيمة لاشينج البحّار 379** (الرسالة 418.76، وCFM وكشف التوزيع 418.86): لا يُفترضان. لازمان لاعتماد بيانات أغسطس نهائيّاً، ولا يوقفان طلبَي الدمج.
- **قالب البنك غير متاح:** نطاق هذا الإصدار كشف Excel عامّ، لا ملفٌّ معتمدٌ للرفع المباشر إلى البنك.
- **التصدير لا يعني الدفع:** لا تحويلات، ولا تأكيد سداد، ولا قيود محاسبيّة.

## صاحب صلاحية الاعتماد

- غياب المتغيّر أو فساده = **لا معتمد**: كلّ اعتمادٍ مرفوض.
- لا يُمنح لكلّ أدمن، ولا يُعدَّل من الواجهة.
- الاعتماد يشمل إصدارات المرتّبات وحسابات الصرف وتفويضات المستفيد.

## أسعار الصرف

- من جدول `exchange_rates` القائم، لشهر الدورة نفسه فقط. لا صفّ `default` ولا قيمةٌ مضمَّنة.
- الإدخال «١ EUR = X USD» بستّ منازل على الأكثر، ويُخزَّن مقلوباً (وحداتٌ لكلّ دولار) بخمسة عشر رقماً معنويّاً، ويُستردّ بستّ منازل مطابقاً للمدخَل حرفيّاً. التحويل: المبلغ × q(من) ÷ q(إلى) ثمّ تقريبٌ واحد.
- الكتابة ذرّيّة لعملةٍ واحدة (`ExchangeRatesService.setOne`)، ولمن يملك شاشة التقارير.
- **بطاقة الأسعار في شاشة التقارير** (`PUT api/exchange-rates/:month`) تمرّ بالقفل نفسه الذي يأخذه
  إدخال أسعار المرتّبات واعتماد إصداراتها (`crew_salary:fx:<month>`)، وترسل الأسعار كما قرأتها:

```
{ "rates": { ... }, "base": { ... } }
```

  - إن تغيّر الشهر منذ قراءتها ⇒ 409، وتُعيد البطاقة التحميل ولا يضيع تحديث أحد.
  - حفظٌ بلا `base` (صفحةٌ قديمة) ⇒ 428 «حدِّث الصفحة».
  - العملات التي ليست في قائمة البطاقة تبقى كما هي.
  - فلا يُعتمد إصدارٌ بسعرٍ تغيّر أثناء الاعتماد: إمّا ينتظر الحفظ حتّى ينتهي الاعتماد، أو يسبقه فتختلف البصمة ويُرفض الاعتماد.

## الدفعات: «خرج» ليس «صُرف»

- كلّ دفعةٍ تُسجِّل صفوفها التي خرجت فعلاً (`crew_salary_export_rows`) — لا لقطة الإصدار كلّها.
- الحالة التي خرجت ثمّ تغيّرت (مبلغاً أو حساباً أو عملة) **لا تُخصم ولا تُعاد آليّاً**؛ تظهر في
  «حالاتٌ خرجت ثمّ تغيّرت» وتنتظر قرار المالك الموثَّق على آخر صفٍّ خرج لها:
  - **استبدال**: ما خرج لم يُنفَّذ ⇒ يُعلَّم صفّه «مُستبدَلاً» ويخرج الصافي الجديد كاملاً.
  - **تسوية**: ما خرج نُفِّذ ⇒ يخرج مبلغٌ إضافيّ يكتبه المالك (موجب، لا يتجاوز الصافي الجديد).
  - **إبقاء**: لا يخرج شيء (ومنه النقص: استرداده خارج هذه الشاشة).
- القرار مربوطٌ بالمحتوى الجديد نفسه: تعديلٌ لاحق يحتاج قراراً جديداً، والقرار يُستهلك مرّةً واحدة.
- **تغيّر العملة يغيّر مفتاح الحالة** (`<بحّار>:<عملة>`). لذلك علاقة استبدالٍ صريحة:
  - عند التقديم تحمل الحالة الجديدة `replaces_keys` في لقطة الإصدار: مفاتيح غابت من الدورة وما زال لها
    اعتمادٌ ساري، **للبحّار نفسه ومن المصدر نفسه** (CFM أو تكميليّ) — لا لمجرّد تطابق رقم البحّار.
  - الاعتماد يتحقّق منها تحت القفل (إن تغيّرت ⇒ أعِد التقديم) ثمّ يُطفئ اعتماد الحالة القديمة.
    فالإصدار القديم لا يُخرج منها دفعةً جديدة أبداً («حلّ محلّها الإصدار N»)، وملفّاته الصادرة تبقى تاريخيّة.
    وبقيّة حالات الإصدار الجزئيّ القديم تبقى معتمدةً وتخرج منه.
  - وما خرج للبحّار تحت المفتاح الغائب يُعدّ خروجاً سابقاً للحالة الجديدة، فتنتظر قرار المالك ولا تخرج كاملةً.
  - حالتان قائمتان معاً للبحّار نفسه (بعملتين) مستقلّتان.
- **القرار على الحالة كما رآها المالك:** يُرسل مع القرار بصمة الحالة وإصدارها المعروضان
  (`expected_hash`، `expected_version_id`)، ويُطابَقان تحت قفل الدورة. تغيّرت الحالة منذ العرض (إصدارٌ أحدث،
  مبلغ، حساب، عملة) ⇒ 409 بلا قرار، وتُحدَّث اللوحة ويُعاد القرار. وغيابهما ⇒ 428 — لا يُربط القرار بالأحدث تلقائيّاً.
- **استبدالٌ والصافي الجديد ليس موجباً:** يُلغى ما خرج فوراً بالقرار نفسه (صفوفه «مُستبدَلة» بمعرّف القرار) ولا صفّ بديل.
  وما أُلغي بلا صفٍّ ساري لا يخرج تلقائيّاً بعد ذلك.
- التصدير كلّه داخل قفل الدورة (القفل نفسه الذي يأخذه الاعتماد): يُعاد قراءة الإصدار والاستحقاقات
  والصفوف والقرارات بعد القفل، ثمّ يُسجَّل الملفّ وصفوفه في المعاملة نفسها.
- ما يُقرَّر بعد دفعةٍ يخرج في دفعةٍ تالية للإصدار نفسه (`…-B2`)، وكلّ دفعةٍ تُنزَّل كما خرجت:

```
GET api/crew-salaries/exports/:id/file
```


## ملفّات PDF

- وثائق الهويّة والعقود (بالاسم) لا يُستخرج نصّها.
- الاستخراج في عمليّةٍ فرعيّة معزولة بمهلةٍ وحدٍّ للمخرَج (`pdf-parse`).
- المستند الماليّ المعروف اليوم: كشف توزيع اللاشينج — مرجعٌ يُظهر التعارض مع الرسالة ولا يستبدلها.

## الاختبارات

```
npx jest src/modules/crew-salaries
npm run test:pg
```

- ملفّ الفحص `docs/crew-salaries-verify.sql` مُختبَرٌ في `crew-salary.migration.pg-spec`: قبل الهجرة وبعدها، وأنّه يكشف صلاحيّةً لدورٍ عامّ وRLS معطَّلة ومشغّلاً معطَّلاً، وأنّه لا يكتب شيئاً.

- العنقود المؤقّت في مجلّد النظام المؤقّت، والتهيئة الأولى ~٩٠ ثانية، والقواعد UTF8 صراحةً.
- التنظيف بعد الاختبار يُنهي ما ثبتت ملكيّته وحده: الـ postmaster المسجَّل عند الإقلاع (معرّفه ووقت نشوئه) وأبناؤه — لا مطابقة نصّ، فلا يُمسّ عنقودٌ آخر ولا عاملٌ يتيمٌ منه (`test/pg/owned-processes.cjs`).

عيّنة حقيقيّة (لا تدخل Git أبداً):

```
CREW_SAMPLE_DIR=<مجلّد فيه aug.msg و cfm_usd.xlsx و cfm_eur.xlsx> npx jest crew-salary.sample
CREW_SAMPLE_DIR=<المجلّد نفسه> npm run test:pg -- crew-salaries.sample
```

## حدود هذه المرحلة

- لا إرسال تحويلات، ولا تأكيد سداد، ولا قيود محاسبيّة. «صُدِّر» ليست «سُدِّد».
- كشف الصرف Excel عامّ، لا يُسمّى «جاهزاً للبنك». قالب كلّ بنك يُضاف لاحقاً.
- الرقم القوميّ لا يُقرأ ولا يُخزَّن: لا قالب بنكٍ معتمد يطلبه بعد.
- رسائل الخادم (الأخطاء وتفاصيل القضايا) بالعربيّة؛ الواجهة نفسها بالعربيّة والإنجليزيّة.
- ملفّات الرسالة تُخزَّن داخل القاعدة (`bytea`)، نحو ١٤MB لكلّ مركبٍ شهريّاً.
