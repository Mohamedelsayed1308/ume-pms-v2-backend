# مرتّبات أطقم السفن — دليل التشغيل

الشاشة: `/dashboard/fleet-crew-salaries`
الواجهة البرمجيّة: `api/crew-salaries`
الوحدة: `src/modules/crew-salaries`

## أوّل تشغيل: بيئة منفصلة قبل الإنتاج

لا يُجرَّب أوّل مرّةٍ على الإنتاج. يُنشأ مشروع Supabase منفصل (أو فرعٌ منه)، وتُطبَّق عليه
الهجرة، ويُقلع عليه باكٌ وفرونتٌ منفصلان:

```
NEXT_PUBLIC_API_URL=<عنوان باك البيئة المنفصلة>
```

ثمّ تُجرى دورة أغسطس كاملة، ثمّ يُفتح باب النشر أدناه.

## بوّابة النشر (كلّ بندٍ يُتحقَّق منه ويُسجَّل)

الترتيب المقترح بعد المراجعة الثالثة. **تجهيزٌ ومراجعة، لا إذنٌ بالنشر** — النشر بطلبٍ صريح من المالك.

1. نسخةٌ احتياطيّة من القاعدة.
2. **نشر الفرونت أوّلاً.** بطاقة الأسعار الجديدة ترسل `base` والباك القائم يتجاهله (يقرأ `rates`)، فلا تتعطّل.
   وشاشة المرتّبات لا تُمنح لأحدٍ بعد — تحتاج الباك الجديد.
3. **إعادة تحميل الصفحات المفتوحة** (بطاقة الأسعار خصوصاً): نشر الفرونت لا يغيّر JavaScript في صفحةٍ مفتوحة.
   ومن لم يُعِد التحميل يُرفض حفظه بعد نشر الباك بـ 428 «حدِّث الصفحة» — لا استبدال أعمى للشهر.
4. **القيد الفريد على `exchange_rates.month`**: كتابة السعر تستعمل `ON CONFLICT (month)`.

```
SELECT conname FROM pg_constraint WHERE conrelid = 'exchange_rates'::regclass AND contype = 'u';
```

5. الهجرة، ثمّ رسالة «RLS مفعّلة، والوصول المباشر مسحوب» (الجداول الأحد عشر، ومنها `crew_salary_export_rows`):

```
node scripts/run-migration.js docs/crew-salaries-up.sql
```

6. نشر الباك، ثمّ `GET /api/health`، ثمّ أنّ `/api/crew-salaries/permissions` يردّ 401 بلا دخول.
7. **أمان الجداول على Supabase نفسه** (لا تكفي PostgreSQL المحلّيّة ولا ملفّ SQL):
   - `relrowsecurity = true` للجداول الأحد عشر.
   - لا صلاحيّات لـ `anon` ولا `authenticated` ولا `service_role`:

```
SELECT grantee, table_name, privilege_type FROM information_schema.role_table_grants
WHERE table_name LIKE 'crew_salary_%' AND grantee IN ('anon','authenticated','service_role');
```

   - طلبٌ من Data API بمفتاح `anon` على أيّ جدول مرتّبات يُرفض.
   - دور اتّصال الباك (DATABASE_URL) هو مالك الجداول — فيعمل رغم RLS.
8. متغيّر المعتمد على Railway:

```
CREW_SALARY_APPROVER_USER_ID=8712bd6f-1880-4fd7-9a7d-8e9976e88eb1
```

أكّد المالك في ٢٧ سبتمبر ٢٠٢٦ أنّ هذا حسابه (`mohamed@ume.com`) وأنّه المعتمد الوحيد.

9. **ثمّ فقط** منح شاشة المرتّبات لمن يلزم. وتعديل أسعار الشركة يبقى لمن يملك شاشة التقارير.
10. سلامة البيانات: استيراد رسالة الشهر وتصديري CFM، ومطابقة الإجماليّات بأرقام المالك المعروفة.
    سعر أغسطس وقيمة لاشينج 379 من المالك قبل اعتماد عيّنة أغسطس نهائيّاً. وكشف الصرف Excel عامّ — لا يوصف ملفّاً معتمداً للرفع المباشر إلى البنك حتّى يأتي قالبه.

التراجع: `docs/crew-salaries-down.sql`. والبوّابة ترفض الحذف إن وُجد أيّ صفّ، إلّا بإعدادٍ على مستوى الجلسة قبل الملفّ:

```
PGOPTIONS='-c crew_salary.force_drop=yes' node scripts/run-migration.js docs/crew-salaries-down.sql
```

## صاحب صلاحية الاعتماد

- غياب المتغيّر أو فساده = **لا معتمد**: كلّ اعتمادٍ مرفوض.
- لا يُمنح لكلّ أدمن، ولا يُعدَّل من الواجهة.
- الاعتماد يشمل إصدارات المرتّبات وحسابات الصرف وتفويضات المستفيد.

## أسعار الصرف

- من جدول `exchange_rates` القائم، لشهر الدورة نفسه فقط. لا صفّ `default` ولا قيمةٌ مضمَّنة.
- الإدخال «١ EUR = X USD» بستّ منازل على الأكثر، ويُخزَّن مقلوباً (وحداتٌ لكلّ دولار) بخمسة عشر رقماً معنويّاً، ويُستردّ بستّ منازل مطابقاً للمدخَل حرفيّاً. التحويل: المبلغ × q(من) ÷ q(إلى) ثمّ تقريبٌ واحد.
- الكتابة ذرّيّة لعملةٍ واحدة (`ExchangeRatesService.setOne`)، ولمن يملك شاشة التقارير.
- **بطاقة الأسعار في شاشة التقارير** (`PUT api/exchange-rates/:month`) تمرّ بالقفل نفسه الذي يأخذه
  إدخال أسعار المرتّبات واعتماد إصداراتها (`crew_salary:fx:<month>`)، وترسل الأسعار كما قرأتها:

```
{ "rates": { ... }, "base": { ... } }
```

  - إن تغيّر الشهر منذ قراءتها ⇒ 409، وتُعيد البطاقة التحميل ولا يضيع تحديث أحد.
  - حفظٌ بلا `base` (صفحةٌ قديمة) ⇒ 428 «حدِّث الصفحة».
  - العملات التي ليست في قائمة البطاقة تبقى كما هي.
  - فلا يُعتمد إصدارٌ بسعرٍ تغيّر أثناء الاعتماد: إمّا ينتظر الحفظ حتّى ينتهي الاعتماد، أو يسبقه فتختلف البصمة ويُرفض الاعتماد.

## الدفعات: «خرج» ليس «صُرف»

- كلّ دفعةٍ تُسجِّل صفوفها التي خرجت فعلاً (`crew_salary_export_rows`) — لا لقطة الإصدار كلّها.
- الحالة التي خرجت ثمّ تغيّرت (مبلغاً أو حساباً أو عملة) **لا تُخصم ولا تُعاد آليّاً**؛ تظهر في
  «حالاتٌ خرجت ثمّ تغيّرت» وتنتظر قرار المالك الموثَّق على آخر صفٍّ خرج لها:
  - **استبدال**: ما خرج لم يُنفَّذ ⇒ يُعلَّم صفّه «مُستبدَلاً» ويخرج الصافي الجديد كاملاً.
  - **تسوية**: ما خرج نُفِّذ ⇒ يخرج مبلغٌ إضافيّ يكتبه المالك (موجب، لا يتجاوز الصافي الجديد).
  - **إبقاء**: لا يخرج شيء (ومنه النقص: استرداده خارج هذه الشاشة).
- القرار مربوطٌ بالمحتوى الجديد نفسه: تعديلٌ لاحق يحتاج قراراً جديداً، والقرار يُستهلك مرّةً واحدة.
- **تغيّر العملة يغيّر مفتاح الحالة** (`<بحّار>:<عملة>`). لذلك علاقة استبدالٍ صريحة:
  - عند التقديم تحمل الحالة الجديدة `replaces_keys` في لقطة الإصدار: مفاتيح غابت من الدورة وما زال لها
    اعتمادٌ ساري، **للبحّار نفسه ومن المصدر نفسه** (CFM أو تكميليّ) — لا لمجرّد تطابق رقم البحّار.
  - الاعتماد يتحقّق منها تحت القفل (إن تغيّرت ⇒ أعِد التقديم) ثمّ يُطفئ اعتماد الحالة القديمة.
    فالإصدار القديم لا يُخرج منها دفعةً جديدة أبداً («حلّ محلّها الإصدار N»)، وملفّاته الصادرة تبقى تاريخيّة.
    وبقيّة حالات الإصدار الجزئيّ القديم تبقى معتمدةً وتخرج منه.
  - وما خرج للبحّار تحت المفتاح الغائب يُعدّ خروجاً سابقاً للحالة الجديدة، فتنتظر قرار المالك ولا تخرج كاملةً.
  - حالتان قائمتان معاً للبحّار نفسه (بعملتين) مستقلّتان.
- **القرار على الحالة كما رآها المالك:** يُرسل مع القرار بصمة الحالة وإصدارها المعروضان
  (`expected_hash`، `expected_version_id`)، ويُطابَقان تحت قفل الدورة. تغيّرت الحالة منذ العرض (إصدارٌ أحدث،
  مبلغ، حساب، عملة) ⇒ 409 بلا قرار، وتُحدَّث اللوحة ويُعاد القرار. وغيابهما ⇒ 428 — لا يُربط القرار بالأحدث تلقائيّاً.
- **استبدالٌ والصافي الجديد ليس موجباً:** يُلغى ما خرج فوراً بالقرار نفسه (صفوفه «مُستبدَلة» بمعرّف القرار) ولا صفّ بديل.
  وما أُلغي بلا صفٍّ ساري لا يخرج تلقائيّاً بعد ذلك.
- التصدير كلّه داخل قفل الدورة (القفل نفسه الذي يأخذه الاعتماد): يُعاد قراءة الإصدار والاستحقاقات
  والصفوف والقرارات بعد القفل، ثمّ يُسجَّل الملفّ وصفوفه في المعاملة نفسها.
- ما يُقرَّر بعد دفعةٍ يخرج في دفعةٍ تالية للإصدار نفسه (`…-B2`)، وكلّ دفعةٍ تُنزَّل كما خرجت:

```
GET api/crew-salaries/exports/:id/file
```


## ملفّات PDF

- وثائق الهويّة والعقود (بالاسم) لا يُستخرج نصّها.
- الاستخراج في عمليّةٍ فرعيّة معزولة بمهلةٍ وحدٍّ للمخرَج (`pdf-parse`).
- المستند الماليّ المعروف اليوم: كشف توزيع اللاشينج — مرجعٌ يُظهر التعارض مع الرسالة ولا يستبدلها.

## الاختبارات

```
npx jest src/modules/crew-salaries
npm run test:pg
```

- العنقود المؤقّت في مجلّد النظام المؤقّت، والتهيئة الأولى ~٩٠ ثانية، والقواعد UTF8 صراحةً.
- التنظيف بعد الاختبار يُنهي ما ثبتت ملكيّته وحده: الـ postmaster المسجَّل عند الإقلاع (معرّفه ووقت نشوئه) وأبناؤه — لا مطابقة نصّ، فلا يُمسّ عنقودٌ آخر ولا عاملٌ يتيمٌ منه (`test/pg/owned-processes.cjs`).

عيّنة حقيقيّة (لا تدخل Git أبداً):

```
CREW_SAMPLE_DIR=<مجلّد فيه aug.msg و cfm_usd.xlsx و cfm_eur.xlsx> npx jest crew-salary.sample
CREW_SAMPLE_DIR=<المجلّد نفسه> npm run test:pg -- crew-salaries.sample
```

## حدود هذه المرحلة

- لا إرسال تحويلات، ولا تأكيد سداد، ولا قيود محاسبيّة. «صُدِّر» ليست «سُدِّد».
- كشف الصرف Excel عامّ، لا يُسمّى «جاهزاً للبنك». قالب كلّ بنك يُضاف لاحقاً.
- الرقم القوميّ لا يُقرأ ولا يُخزَّن: لا قالب بنكٍ معتمد يطلبه بعد.
- رسائل الخادم (الأخطاء وتفاصيل القضايا) بالعربيّة؛ الواجهة نفسها بالعربيّة والإنجليزيّة.
- ملفّات الرسالة تُخزَّن داخل القاعدة (`bytea`)، نحو ١٤MB لكلّ مركبٍ شهريّاً.
